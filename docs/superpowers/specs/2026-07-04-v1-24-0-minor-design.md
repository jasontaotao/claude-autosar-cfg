## Motivation

v1.22.0 shipped the ODX-D importer + read-only `OdxViewer` modal. The release notes explicitly stated: "Bridge to ARXML + project integration still deferred." v1.24.0 closes that carry-over.

v1.23.0 shipped the DBC→Com/CanIf/PduR bridge as a 3-file atomic write template. v1.24.0 applies the same pattern to ODX→Diagnostic Extract (Dem + Dcm), completing the "import external data → generate ARXML → atomic write to project" capability.

User constraint: "只要ODX->arxml 就好了啊，不需要arxml 导出到odx" (ODX→ARXML only, not the reverse). v1.24.0 is one-way: takes parsed `OdxSummary`, writes Dem + Dcm ARXML.

## Goals

1. **Standalone Diagnostic Extract output** — generate `Dem_Extract.arxml` + `Dcm_Extract.arxml` from a parsed `OdxSummary`. No BSWMD-REF (user merges externally). Mirrors Vector's "Diagnostic Extract" tool output convention.
2. **3-surface coverage** — DTC → `DemEventParameter`; DID → `DcmDspDid`; Routine → `DcmDspRoutine`. All 3 surfaces of v1.22.0's `OdxSummary` are consumed.
3. **2-phase atomic write** — same snapshot + serial rename + rollback pattern as v1.23.0 T1. Renderer surfaces `rolledBack: boolean` on partial failure.
4. **Real-OEM fixture validation** — `samples/odx/Demo_Cdd.odx-d` (Vector CANdelaStudio export, 897 KB) round-trips through the bridge and produces 99 DemEvents / 4 DcmRoutines / 34 DcmDids + concrete DTC `_258` regression assertion.

## Non-Goals (explicit YAGNI)

- **No BSWMD-REF in output** — user merges with their own Dem/Dcm BSWMD. v1.24.0 does NOT vendor a stub BSWMD; it does NOT require the user to install Vector/EB tooling; it does NOT generate the BSWMD-DESTINATION-REF-SHORTTYPE-REF cross-references.
- **No Dcm services (0x14/0x19/0x22/0x2E/0x31) generated** — not in v1.22.0's `OdxSummary`; user adds manually post-merge.
- **No DID/Routine data (length, scaling, encoding)** — would need to parse ODX-INSTANCE elements from .odx-d; defer to v1.24.x PATCH.
- **No reverse direction (ARXML → ODX)** — explicit user constraint.
- **No DebounceAlgorithm / EventPriority config** — BSWMD-coupled; user fills in.
- **No BSWMD merge helper** — the output is standalone; merging is the user's existing toolchain.

## Scope

**In scope (v1.24.0 MINOR)**:
- 1 pure mapper: `odxToDiagnosticExtract({odx, outputDir})` → `{demFile, dcmFile, log, stats}`
- 1 IPC handler: `OdxImportDiagnosticExtractHandler` with 2-phase atomic write
- 1 new IPC channel: `ODX_IMPORT_DIAGNOSTIC_EXTRACT`
- UI: "Export Diagnostic Extract" button in `OdxViewer` modal
- UI: success dialog showing 2 file paths + counts
- Real-OEM fixture test against `Demo_Cdd.odx-d`
- 5 ARXML i18n keys (en + zh-CN) for the new UI
- Release notes + CHANGELOG + user-manual baseline bump

**Out of scope (deferred to v1.24.x PATCH or v1.25.0 MINOR)**:
- Dcm services (0x14/0x19/0x22/0x2E/0x31) generation
- DID/Routine data fields (length, scaling, encoding)
- DebounceAlgorithm / EventPriority config (BSWMD-coupled)
- BSWMD merge helper (requires user toolchain integration)
- Reverse direction (ARXML → ODX)
- Multi-ODX batch import (only single .odx-d per export in v1.24.0)

## Data mapping (detailed)

### DTC → DemEventParameter

ODX DTC fields (per v1.22.0's `OdxDtcSummary`):
```ts
{ id: string; shortName: string; troubleCode: string; displayCode?: string; text?: string }
```

Generated ARXML:
```xml
<DEM-EVENT-PARAMETER>
  <SHORT-NAME>{dtc.shortName}</SHORT-NAME>
  <EVENT-KIND>DEM_EVENT_KIND_SWC</EVENT-KIND>
  <DISPLAY-CODE>{dtc.displayCode ?? dtc.troubleCode}</DISPLAY-CODE>
  <DTC-VALUE>{dtc.troubleCode}</DTC-VALUE>
  <TEXT>...{dtc.text}</TEXT>
</DEM-EVENT-PARAMETER>
```

Notes:
- `EVENT-KIND` defaults to `DEM_EVENT_KIND_SWC` (best-guess for ODX-DTCs; user adjusts in their BSWMD).
- `DISPLAY-CODE` falls back to raw `troubleCode` if `displayCode` is undefined (handles older ODX files without `<DISPLAY-TROUBLE-CODE>`).
- `DTC-VALUE` is the raw wire-format value (e.g. `687361`); `DISPLAY-CODE` is the SAE J2012 form (e.g. `P0A7D01`).
- TEXT element is added only if `dtc.text` is non-empty.
- No `<DEM-BSWM-REF DEST="BSW-MODULE-DESCRIPTION">` — standalone.

### DID → DcmDspDid

ODX DID fields (per v1.22.0's `OdxDidSummary`):
```ts
{ id: string; shortName: string }
```

Generated ARXML:
```xml
<DCM-DSP-DID>
  <SHORT-NAME>{did.shortName}</SHORT-NAME>
  <!-- DcmDspDidInfo is BSWMD-coupled; user adds manually post-merge -->
  <!-- v1.24.x PATCH: parse ODX-INSTANCE for DID data (length, scaling, encoding) -->
</DCM-DSP-DID>
```

### Routine → DcmDspRoutine

ODX Routine fields (per v1.22.0's `OdxRoutineSummary`):
```ts
{ id: string; shortName: string }
```

Generated ARXML:
```xml
<DCM-DSP-ROUTINE>
  <SHORT-NAME>{routine.shortName}</SHORT-NAME>
  <!-- DcmDspRoutineInfo is BSWMD-coupled; user adds manually post-merge -->
  <!-- v1.24.x PATCH: parse ODX-INSTANCE for Routine data (start, stop, request/response format) -->
</DCM-DSP-ROUTINE>
```

### ARXML envelope (both files)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<AUTOSAR xmlns="http://autosar.org/schema/r4.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:schemaLocation="http://autosar.org/schema/r4.0 AUTOSAR_4-4.xsd">
  <AR-PACKAGES>
    <AR-PACKAGE>
      <SHORT-NAME>DiagExtract</SHORT-NAME>
      <ELEMENTS>
        <!-- Dem or Dcm elements go here -->
      </ELEMENTS>
    </AR-PACKAGE>
  </AR-PACKAGES>
</AUTOSAR>
```

Both files share the envelope; only the `ELEMENTS` block differs.

## Atomic write (mirrors v1.23.0 T1)

```
1. Pre-flight: validate outputDir exists + is writable
2. Snapshot existing files at outputDir/{Dem,Dcm}_Extract.arxml (if any)
3. Generate Dem + Dcm content (in-memory)
4. Write Dem to temp file: writeAtomic(outputDir/Dem_Extract.arxml.tmp, demContent)
5. Rename tmp → final: rename(tmp, outputDir/Dem_Extract.arxml)
6. Repeat for Dcm
7. If step 5 or 6 throws:
   - Restore snapshot for both files (if any)
   - Return write-failed with rolledBack: true
8. If both succeed: return success
```

**Reuses**: `writeAtomic` helper from `src/main/fs/writeAtomic.ts` (v1.23.0 T1). No new filesystem helpers needed.

## IPC contract

`src/shared/ipc-contract.ts` (additions):

```ts
export interface OdxImportDiagExtractRequest {
  /** Absolute path to the .odx-d file (parsed by v1.22.0's parseOdxHandler). */
  readonly odxPath: string;
  /** Absolute path to the output directory. Must exist and be writable. */
  readonly outputDir: string;
}

export type OdxImportDiagExtractResponse =
  | {
      readonly kind: 'success';
      readonly demPath: string;
      readonly dcmPath: string;
      readonly log: readonly string[];
      readonly stats: { dtcCount: number; didCount: number; routineCount: number };
    }
  | { readonly kind: 'parse-failed'; readonly error: string }
  | { readonly kind: 'write-failed'; readonly error: string; readonly rolledBack: boolean };

export const ODX_IMPORT_DIAGNOSTIC_EXTRACT = 'odx-import-diagnostic-extract' as const;
```

## Risks

1. **No BSWMD-REF in output** = the Dem/Dcm ARXML won't pass strict AUTOSAR schema validation standalone. **Mitigation**: documented in release notes + ARXML header comment ("Diagnostic Extract — merge with your Dem/Dcm BSWMD post-export"). Same caveat Vector's Diagnostic Extract tool ships.
2. **Real-OEM fixture may have quirks** we didn't catch in T4 unit tests. **Mitigation**: T4 is a SHIP-BLOCKING test (per v1.22.0 T4 / v1.23.0 T4 precedent). If it fails, we fix the mapper, not the test.
3. **Atomic write regression risk** — v1.23.0 T1 shipped a 2-phase commit with snapshot rollback; we're reusing `writeAtomic`. **Mitigation**: T2's write-failed test exercises the rollback path with a pre-existing file snapshot.
4. **i18n bypass pattern** (per v1.23.1 T1 L1 lesson) — if T3's diagnostic string is hardcoded English, the renderer breaks zh-CN. **Mitigation**: all 5 new keys go through `t(locale, key, params)`; i18n parity test (`src/shared/__tests__/i18n.test.ts`, 88 cases) is updated to include the 5 new keys × 2 locales.
