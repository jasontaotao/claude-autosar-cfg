# v1.27.0 MINOR — Dcm Services Generator (ODX + xlsx Integrated) Design Spec

> **Design date:** 2026-07-05
> **Status:** DRAFT (awaiting user review)
> **Goal:** Add a NEW IPC handler `dcmConfigHandler` that combines ODX-extracted `DcmDspDid`/`DcmDspRoutine` containers (from v1.24.0's `odxToDiagnosticExtract`) with xlsx-configured Dcm service instances (5 UDS kinds: 0x14 ClearDTC, 0x19 ReadDTC, 0x22 ReadDataById, 0x2E WriteDataById, 0x31 RoutineControl) into a single Dcm-Config ARXML. Builds on the v1.26.0 BSWMD-driven mapper infrastructure.

## Background

### Why now

v1.25.x PATCH T3 added a Demo BSWMD enrichment exposing `PduRRoutingPaths` regression (v1.25.2 reverted it). v1.25.2 + v1.26.0 closed the brittleness that allowed hardcoded BSWMD paths to drift silently. The Dcm services generator was explicitly deferred from v1.25.2 release notes Out of Scope and v1.26.0 release notes; v1.27.0 is the natural follow-up now that:
- v1.26.0 ships the `lookupContainerDef`-based BSWMD-driven mapper (eliminates the brittleness class)
- v1.24.0 ships `odxToDiagnosticExtract.dcmContent` (DIDs/Routines as standalone ARXML, but no service binding)

### The integration gap

ODX (ISO 22901) diagnostic descriptions contain 3 pieces of data relevant to Dcm configuration:

| ODX element | Dcm usage | Current v1.24.0 coverage |
|---|---|---|
| DTC (Diagnostic Trouble Code) | `DemEventParameter` (Dem side) | ✅ Standalone Extract → `Dem_Extract.arxml` |
| DID (Data Identifier) | 0x22 ReadDataById + 0x2E WriteDataById reference | ✅ Standalone Extract → `Dcm_Extract.arxml` |
| Routine | 0x31 RoutineControl references | ✅ Standalone Extract → `Dcm_Extract.arxml` |
| Dcm service configs (0x14/0x19/0x22/0x2E/0x31 service instances) | `DcmDsp*` per-service | ❌ Not generated |

The user must currently import the extract file (e.g., via DaVinci/EB tresos/GENy) and manually configure the 5 Dcm service instances to reference the DIDs/Routines. This is friction: every project hand-crafts services that could be data-driven from `.xlsx` rows + the extract.

### Existing infrastructure leveraged

- `src/core/bridge/odxToDiagnosticExtract.ts` (v1.24.0, 433 LOC) — pure ODX→Standalone-ARXML; produces `dcmContent` string
- `src/core/bridge/xlsxToEcucBatch.ts` (v1.26.0, +30% net LOC) — BSWMD-driven mapper for Com-stack kinds; signature pattern replicated for Dcm
- `src/core/bridge/demoBswmdLoader.ts` (v1.26.0 T1, 48 LOC) — `parseDemoBswmds(arxmlStrings): ReadonlyMap<string, BswModuleDef>`
- `src/core/project/bswmd.ts:458` — `lookupContainerDef(BswModuleDef, string): ContainerDef | null`
- v1.23.0 atomic-write pattern (snapshot + rollback) for transactional file output
- `src/core/generator/diagnostics.ts` (46 LOC) — shared diagnostic error-reporting facility (ERROR/WARNING/INFO severity; ~17 diagnostic codes; reused by ECUC + BSW generators)

## Goal

Add a NEW IPC handler that produces a merged Dcm ARXML document from ODX + xlsx inputs. The 5 Dcm service kinds become sheet names in the xlsx side; each sheet row produces 1 Dcm service instance that references DIDs/Routines from the ODX extract. Output is a single ARXML that contains both the ODX-derived `DcmDspDid`/`DcmDspRoutine` containers AND the user-configured `DcmDsp*` service instances, atomically written with snapshot rollback.

After v1.27.0:

- User has 1 ODX file with DIDs/Routines → imports via new IPC handler
- User has 1 `.xlsx` with rows for 5 Dcm service kinds → same handler
- Output: `Dcm_Config.arxml` standalone file (matching v1.24.0 convention; no BSWMD-REF; user merges with their Dcm BSWMD via tooling)

## Non-Goals

- **Dem service generator** — Dem has different concerns (DTC mapping, debouncing); out of scope (separate sub-project if pursued)
- **xlsx-only Dcm services (no ODX)** — explicitly rejected at Q1 in favor of ODX integration
- **Streaming for huge `.xlsx`** (5MB+) — YAGNI; defensive size cap only
- **ARXML → ODX reverse direction** — future scope
- **Generic any-kind batch import** — each kind has its own BSWMD contract; YAGNI for abstraction layer
- **Replacing the existing `xlsxEcucBatchImportHandler`** — v1.26.0 xlsx handler stays untouched for Com-stack kinds; new handler is parallel for Dcm

## Architecture

### New IPC handler: `dcmConfigHandler`

```ts
// src/main/ipc/dcmConfigHandler.ts
export async function dcmConfigHandler(
  args: {
    readonly odxPath: string;                   // existing ODX file on disk
    readonly xlsxRows: readonly EcucInstanceRow[]; // 5 Dcm sheet kinds + params
    readonly resolutions?: ReadonlyMap<string, 'overwrite' | 'skip'>;
    readonly outputPath?: string;              // defaults to <projectDir>/Dcm_Config.arxml
  },
): Promise<IpcResult<DcmConfigResult>>
```

**Responsibilities** (in order):
1. Read ODX file from `args.odxPath`; parse via existing v1.22.0 `parseOdxHandler` (returns `OdxSummary`)
2. Load Dcm BSWMD from project's `samples/arxml/demo-ecu/bswmd/Bsw_Dcm_Bswmd.arxml` (or real-OEM equivalent if project overrides)
3. Call `dcmConfigPipeline({ odx, xlsxRows, bswmd, projectManifestPath })` → produces merged Dcm ARXML
4. Atomic-write the ARXML to `args.outputPath` with snapshot rollback (v1.23.0 pattern)
5. Return `IpcResult<DcmConfigResult>` with counters

### Pipeline: `dcmConfigPipeline`

```ts
// src/core/bridge/dcmConfigPipeline.ts
export async function dcmConfigPipeline(
  request: {
    readonly odx: OdxSummary;
    readonly xlsxRows: readonly EcucInstanceRow[];
    readonly bswmd: BswModuleDef;          // single Dcm module
    readonly projectManifestPath: string;
  },
  options?: { readonly snapshotsDir?: string },
): Promise<DcmConfigResult>
```

**Steps**:
1. `odxToDiagnosticExtract(request.odx).dcmContent` → standalone Dcm extract (DIDs + Routines as `<DcmDspDid>`/`<DcmDspRoutine>` elements)
2. Parse the standalone content → mutate a cloned ArxmlDocument (the "extract doc")
3. `xlsxDcmServicesToEcucBatch(request.xlsxRows, new Map([['Dcm', request.bswmd]]))` → service PatchSteps
4. Apply each patch to the extract doc via existing engine `applyPatchSteps`
5. Validate cross-document references: for each `DcmReadDataById`/`DcmWriteDataById`/`DcmRoutineControl` row, confirm the `didShortName`/`routineShortName` exists in the ODX extract. **Throw with diff if not.**
6. Serialize via `serializeArxml`
7. Return `DcmConfigResult` (xml string + counters)

### New mapper: `xlsxDcmServicesToEcucBatch`

```ts
// src/core/bridge/xlsxDcmServicesToEcucBatch.ts
export function xlsxDcmServicesToEcucBatch(
  rows: readonly EcucInstanceRow[],
  bswmds: ReadonlyMap<string, BswModuleDef>,
): PatchStep[]
```

**Mirrors v1.26.0's `xlsxToEcucBatch`** with:
- `SHEET_TO_MODULE` const extended with 5 Dcm entries (all map to module shortName `'Dcm'`):
  ```ts
  const SHEET_TO_MODULE = {
    DcmClearDTC: 'Dcm',
    DcmReadDTC: 'Dcm',
    DcmReadDataById: 'Dcm',
    DcmWriteDataById: 'Dcm',
    DcmRoutineControl: 'Dcm',
  } as const;
  ```
- **`SHEET_TO_CONTAINER_SHORT_NAME` const (NEW seam for v1.27.0):** maps user-facing xlsx sheet names to **canonical AUTOSAR `DcmDsp*` container shortNames** declared in the BSWMD. This is the abstraction-vs-canonical seam that fixes the v1.25.x `claude-autosarcfg-canonical-autosar-pdur-paths-not-tables` violation (same lesson v1.25.2 PATCH T1 was created to honor). Per v1.27.0 design decision: xlsx sheet names stay abstracted for ergonomics (a user typing `DcmClearDTC` in Excel is friendlier than `DcmDspClearDTC`); BSWMD-side container shortNames use canonical AUTOSAR spellings.

  | xlsx sheet name (user-facing) | BSWMD container shortName (canonical AUTOSAR) |
  |---|---|
  | `DcmClearDTC` | `DcmDspClearDTC` |
  | `DcmReadDTC` | `DcmDspReadDTCInformation` |
  | `DcmReadDataById` | `DcmDspDid` (canonical parent for both 0x22 + 0x2E) |
  | `DcmWriteDataById` | `DcmDspDid` (same parent as 0x22; mapper emits `definitionRef` to differentiate) |
  | `DcmRoutineControl` | `DcmDspRoutine` |

  ```ts
  const SHEET_TO_CONTAINER_SHORT_NAME: Readonly<Record<DcmSheetKind, string>> = {
    DcmClearDTC: 'DcmDspClearDTC',
    DcmReadDTC: 'DcmDspReadDTCInformation',
    DcmReadDataById: 'DcmDspDid',
    DcmWriteDataById: 'DcmDspDid',
    DcmRoutineControl: 'DcmDspRoutine',
  };
  ```

  **Lookup logic in the row loop:**
  ```ts
  const lookupKey = SHEET_TO_CONTAINER_SHORT_NAME[row.sheet];
  const containerDef = lookupContainerDef(bswmd, lookupKey);
  ```
- Same 3 fail-fast error classes (unknown sheet / missing module / missing container) — text-stable regexes match v1.26.0's existing patterns
- Per-row emits `add-child` + per-param `set-param` PatchSteps per existing v1.26.0 contract
- File-local — not a global mutable const (each mapper module owns its sheet→module mapping)

### ODX-Dcm linkage validation

Cross-document reference check is the **new** error class for v1.27.0. Not present in v1.26.0:

| Service kind | ODX element referenced | Validation |
|---|---|---|
| `DcmReadDataById` (0x22) | `DcmDspDid` (from ODX) | `didShortName` must exist in ODX extract |
| `DcmWriteDataById` (0x2E) | `DcmDspDid` (from ODX) | same |
| `DcmRoutineControl` (0x31) | `DcmDspRoutine` (from ODX) | `routineShortName` must exist |
| `DcmClearDTC` (0x14) | none | no linkage |
| `DcmReadDTC` (0x19) | none | no linkage (0x19 reads DTCs from Dem, not ODX DIDs) |

**Error message shape**:
```
ODX-Dcm linkage broken:
  Sheet 'DcmReadDataById', row 'EngineTemp': referenced DID 'NotInOdx' not found.
  Available DIDs from ODX: Vbatt, EngTemp, Vin, ...
```

Surfaces exact mismatch + valid alternatives so the user can correct the `.xlsx` row directly.

### New fixtures

**`samples/arxml/demo-ecu/bswmd/Bsw_Dcm_Bswmd.arxml`** (NEW): canonical demo-ecu Dcm BSWMD declaring 4 service containers with **canonical AUTOSAR `DcmDsp*` shortNames**:

```xml
<ECUC-MODULE-DEF><SHORT-NAME>Dcm</SHORT-NAME>
  <CONTAINERS>
    <ECUC-PARAM-CONF-CONTAINER-DEF><SHORT-NAME>DcmDspClearDTC</SHORT-NAME>...</ECUC-PARAM-CONF-CONTAINER-DEF>
    <ECUC-PARAM-CONF-CONTAINER-DEF><SHORT-NAME>DcmDspReadDTCInformation</SHORT-NAME>...</ECUC-PARAM-CONF-CONTAINER-DEF>
    <ECUC-PARAM-CONF-CONTAINER-DEF><SHORT-NAME>DcmDspDid</SHORT-NAME>...</ECUC-PARAM-CONF-CONTAINER-DEF>
    <ECUC-PARAM-CONF-CONTAINER-DEF><SHORT-NAME>DcmDspRoutine</SHORT-NAME>...</ECUC-PARAM-CONF-CONTAINER-DEF>
  </CONTAINERS>
</ECUC-MODULE-DEF>
```

**Note on container count**: The fixture declares 4 containers, not 5, because canonical AUTOSAR uses `DcmDspDid` as the **shared parent** for both 0x22 (ReadDataById) and 0x2E (WriteDataById). The mapper differentiates the two services via per-row `definitionRef` emitted in the PatchSteps (not via separate container shortNames). This matches AUTOSAR's actual structure — `DcmDspDidData` is NOT a top-level container in canonical AUTOSAR (it is an ELEMENT under `DcmDspDid`).

The mapping from xlsx sheet names (5 user-facing kinds) to BSWMD container shortNames (4 canonical AUTOSAR kinds) is mediated by the `SHEET_TO_CONTAINER_SHORT_NAME` const in the mapper (see `xlsxDcmServicesToEcucBatch` architecture section above).

Mirrors the cross-reference pattern from `claude-autosarcfg-canonical-autosar-pdur-paths-not-tables` lesson: BSWMD container shortNames match canonical AUTOSAR spec at `samples/arxml/AUTOSAR_MOD_ECUConfigurationParameters.arxml`.

**`samples/comstack-existing-fixture/Dcm.bswmd.arxml`** (NEW): Vector-derived real-OEM-style Dcm BSWMD for cross-vendor invariant verification. Must use the same canonical `DcmDsp*` shortNames as the demo fixture (cross-vendor invariant).

### BSWMD enrichment invariant (BSWMD-side, not xlsx-side)

Per the v1.25.0 errata lesson: every new BSWMD container shortName is cross-referenced against canonical AUTOSAR + the real-OEM fixture before commit. For v1.27.0, the BSWMD-side container shortNames use canonical AUTOSAR `DcmDsp*` spellings (the user-facing xlsx sheet names stay abstracted for ergonomics; the seam between abstracted and canonical is the `SHEET_TO_CONTAINER_SHORT_NAME` const).

## Data Flow

```
┌──────────────────────────────────────────────────────────────┐
│ User action: invoke IPC 'dcm:config' with {odxPath, xlsxRows} │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│ dcmConfigHandler                                             │
│   1. readFileSync(odxPath) → ARXML string                    │
│   2. parseOdxHandler(odxXml) → OdxSummary                    │
│   3. parseDemoBswmds({ Dcm: readFileSync(Bsw_Dcm_Bswmd) })   │
│      → ReadonlyMap<'Dcm', BswModuleDef>                      │
│   4. dcmConfigPipeline(...)                                  │
│   5. atomicWrite(outputPath, result.dcmConfigXml)           │
│   6. return IpcResult<DcmConfigResult>                       │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│ dcmConfigPipeline                                            │
│   a. odxToDiagnosticExtract(odx).dcmContent                  │
│      → standalone Dcm ARXML (DIDs + Routines)                │
│   b. parse(dcmContent) → mut_doc (ArxmlDocument)            │
│   c. xlsxDcmServicesToEcucBatch(xlsxRows, bswmds)           │
│      → PatchStep[] (5 kinds)                                 │
│   d. ODX-Dcm linkage validation                              │
│      → throw if didShortName / routineShortName missing     │
│   e. applyPatchSteps(mut_doc, patches)                       │
│   f. serializeArxml(mut_doc) → xml string                   │
│   g. return { dcmConfigXml: xml, ...counters }               │
└──────────────────────────────────────────────────────────────┘
```

**Single ARXML output**: the file contains BOTH the ODX-derived `DcmDspDid`/`DcmDspRoutine` containers AND the xlsx-configured `DcmDsp*` service instances. User merges with their Dcm BSWMD via tooling (DaVinci/EB tresos/GENy).

## Error Handling

| Error class | Trigger | Error message shape |
|---|---|---|
| Unknown sheet | `sheet` not in `SHEET_TO_MODULE` const | `Unrecognized sheet name: '<X>' (allowed: ...)` |
| Module missing | `bswmds.get('Dcm') === undefined` | `BSWMD map missing module 'Dcm' (...). Provided modules: ...` |
| Container missing | `lookupContainerDef(bswmd, sheet)` returns null | `Container '<X>' not found in BSWMD module 'Dcm'. ...` |
| **ODX-Dcm linkage broken** | xlsx row's `didShortName`/`routineShortName` not in ODX extract | `ODX-Dcm linkage broken: Sheet '<X>', row '<Y>': referenced <DID\|Routine> '<Z>' not found. Available: ...` |
| ODX file unreadable | `readFileSync(odxPath)` fails | propagated from `node:fs`; surfaced via `IpcResult.error` |
| ODX malformed | `parseOdxHandler` returns Err | `Failed to parse ODX at '<path>': <message>` |
| Output write fails | atomic-write snapshot rollback | propagated via `IpcResult.error` |

All 5 fail-fast errors are thrown inside `dcmConfigPipeline` or `dcmConfigHandler` — never emitted as patches that get silently filtered (cf. v1.25.x's silent `path-not-found` masking).

## Risks and Mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Real-OEM Dcm BSWMD shape differs from demo (different shortName casing, different sub-containers) | Medium | Test exercises both; if divergence, prefer canonical AUTOSAR shortName (per errata lesson) |
| ODX parser doesn't expose DID shortNames in the format the mapper expects | Low | v1.24.0 ships `odxToDiagnosticExtract.dcmContent` with `<DcmDspDid>` instances; shortName is the canonical key |
| `applyPatchSteps` semantics for new Dcm sheet kinds not yet exercised | Low | T5 verification exercises end-to-end with snapshot rollback |
| Atomic-write race with concurrent edits to Dcm_Config.arxml | Low | v1.23.0 snapshot+rollback handles this; reuse |
| v1.26.0 path-strip dual-source-of-truth (mapper strips `/<docRootPkg>/`, handler re-prepends) leaks into Dcm path | Medium | Reuse same convention; document in inline comment |
| ODX-Dcm linkage error surface ambiguity (which DIDs are available? — extract may have 100+) | Low | Truncate the "Available:" list to first 10 + show count |
| New IPC channel name conflicts with existing IPC channels | Low | `dcm:config` follows `xlsx:batchImport` naming convention |

## Carry-over / Out of Scope

Deferred to **v1.28.0+ MINOR**:
- Dem service generator (DTC mapping + debouncing)
- Dcm-side error-trace configuration (DcmDspDiagnosticSession)
- DcmDsl (Dcm data-link layer) configuration
- Negative Response (NRC) customization per service
- Security access (0x27) configuration (out of original 5 UDS kinds but commonly grouped)
- Real-OEM Dcm BSWMD authoring guide (if Vector export contract differs)

Long-term (v1.29.0+):
- Auto-infer 5 service kinds from BSWMD (drop `SHEET_TO_MODULE` const for Dcm) — analogous to v1.26.0's full BSWMD-driven path
- Generic BSWMD-driven bridge for any module (Dcm+Dem+Com+...) — refactor opportunity
