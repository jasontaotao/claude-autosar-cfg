## Background

### v1.25.0 / v1.25.1 timeline

- **v1.25.0** shipped at `980d04a` with a bridge mapper (`src/core/bridge/xlsxToEcucBatch.ts`) that hardcodes BSWMD-side paths for 5 Com-stack kinds. At the time, the demo project's PduR BSWMD declared the container `PduRRoutingPaths` (pre-T3 demo shape), so the mapper's hardcoded `PduR/PduRRoutingPaths/PduRRoutingPath` matched.
- **v1.25.1 PATCH T3** enriched the demo BSWMDs to AUTOSAR-spec-correct container names: `PduRRoutingTables` (with `Tables`, not `Paths`). The mapper's hardcoded path was NOT updated — T3 followed spec Risks option (b): "adjust the test expectation since the new behavior is correct". Two existing test assertions were relaxed from `>= 1` to `>= 0` (`perFile.PduR` and `addedCounts.pduR`).
- **v1.25.1 release notes** documented this as a "Known consequence": bridge mapper realignment deferred to a follow-up PATCH.

### Why this matters

The bridge mapper's hardcoded path is silently soft-filtered by the engine's `path-not-found` advisory filter, so the user does NOT see an error — the `add-child` step simply doesn't land. The PduR kind is silently dropped from the import. For end users, this means:

- A `.xlsx` row tagged `sheet: 'PduRRoutingPath'` looks valid (no error).
- The PduR instance is never created in the committed ARXML.
- The user has no diagnostic indicating the failure.

The v1.25.0 T4 75-row ship-blocking test masked this bug because its `ComIPduDirection=SEND` textual-pin assertion coincidentally matched BSWMD defaults (similar to how the C1 integer-default bug was masked).

## Goal

Realign the bridge mapper's hardcoded `PduRRoutingPath` parent path to match the v1.25.1-enriched BSWMD's `PduRRoutingTables` container name. Restore the 2 test assertions relaxed in v1.25.1 PATCH. Close the documented Known Consequence in v1.25.1 release notes.

## Non-Goals

- **BSWMD-driven dynamic lookup** — the right long-term fix is to refactor the mapper to derive paths from BSWMD via `lookupContainerDef`. This is OUT OF SCOPE for v1.25.2 PATCH (it would change the mapper's signature and ripple to both the xlsx import handler and the DBC bridge). Defer to v1.26.0 MINOR where a mapper refactor is more appropriate.
- **Casing fixes** — the mapper still uses `ComIpdu` (lowercase `p`) for the ComIPdu kind, which matches the demo BSWMD's casing exactly. Not a bug. Leave as-is.
- **Other sheet kinds** — `ComIPdu` / `ComSignal` / `CanIfTxPdu` / `CanIfRxPdu` paths in the mapper all match the v1.25.1-enriched BSWMDs exactly. Only `PduRRoutingPath` is misaligned.
