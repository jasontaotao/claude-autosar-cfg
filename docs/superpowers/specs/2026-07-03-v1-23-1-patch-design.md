## Goal

Close 3 deferred issues from v1.23.0 ship cycle in a single PATCH:

1. **T1 Cross-File Atomic Write** (real bug, important): T3 IPC `dbCImportComStackHandler` uses `Promise.allSettled` + per-file `writeAtomic`. ## Architecture

### T1 — Cross-File Atomic Write

The current `dbCImportComStackHandler` flow (v1.23.0):

```
1. Parse DBC
2. Read 3 ECUC ARXML files in parallel
3. Generate bridge plan
4. For each file: parse → apply patches → serialize
5. Promise.allSettled([writeAtomic(Com), writeAtomic(CanIf), writeAtomic(PduR)])  ← BUG
6. If any failed, return write-failed; first file is already committed
```

The new flow (v1.23.1):

```
1. Parse DBC
2. Read 3 ECUC ARXML files in parallel (originals)
3. Generate bridge plan
4. For each file: parse → apply patches → serialize (in-memory new contents)
5. PHASE 1: Promise.all([writeFile(tmp1), writeFile(tmp2), writeFile(tmp3)])  ← write tmp files
6. PHASE 2: try sequential atomic rename(tmp1, com1), atomic rename(tmp2, canif1), atomic rename(tmp3, pdur1)
7. On phase-2 failure: best-effort writeAtomic rollback using originals from step 2
8. Return BridgeWriteResult with rolledBack: boolean
```

**Why snapshot + 2-phase works**:

- `writeAtomic` is already tmp + rename per file. We're composing 3 atomic-per-file operations into a "transactional" cross-file operation by sequencing the renames (the write tmp files can be parallel; the renames must be serial so we can rollback between them).
- Snapshot is in-memory (`{ com: string, canIf: string, pduR: string }`) — no IO cost.
- Rollback uses the same `writeAtomic` helper, so the rollback is itself atomic per file.

**Why not staging dir**: Windows NTFS rename across directories is not atomic. Per-directory rename (same dir, different filename) IS atomic. Our tmp files are in the same dir as the targets.

**Why not git/backup**: project files are not git-tracked (this is a user data dir). Backup would require its own IO race.

### T2 — i18n Interface Split

Current: `src/shared/i18n.ts` (863 lines, ~85 keys, 16 namespaces). All callers do `import { type Messages, type MessagesEn, type MessagesZhCN } from 'shared/i18n'`.

New structure:

```
src/shared/i18n/
├── index.ts          ← barrel: re-exports Messages/MessagesEn/MessagesZhCN
├── types.ts          ← Messages = AppMessages & DialogMessages & DbcMessages & OdxMessages
├── app.ts            ← AppHeader menu, buttons, status (was namespace 'app.*')
├── dialog.ts         ← modal common, error generic (was 'common.*' and 'dialog.*')
├── dbc.ts            ← 16 dbc.import.* keys (DBC bridge v1.23.0)
├── odx.ts            ← 22 odx.viewer.* keys (ODX viewer v1.22.0)
```

The barrel (`index.ts`) re-exports the union type and both locale tables, so **all 6 caller files (DbcImportWizard, AppHeader, App.tsx, etc.) import from `'shared/i18n'` and don't change**.

The ceiling test in `src/shared/__tests__/i18n.test.ts:771-782` asserts `< 900`; after split, the largest file (`dbc.ts`) is ~150 lines, well under.

```ts
export type DbcImportComStackResponse =
  | {
      readonly ok: true;
      readonly value: {
        readonly addedCounts: {
          readonly com: number;
          readonly canIf: number;
          readonly pduR: number;
        };
      };
    }
  | {
      readonly ok: false;
      readonly error:
        | { readonly kind: 'read-failed' | 'bridge-failed'; readonly message: string }
        | { readonly kind: 'write-failed'; readonly message: string; readonly rolledBack: boolean };
    };
```

### T1 — `BridgeWriteResult` type (internal to handler, not exposed)

```ts
// Internal — not part of IPC contract
type WritePhase = 'write-tmp' | 'rename' | 'rollback';
type BridgeWriteResult =
  | { readonly kind: 'ok' }
  | {
      readonly kind: 'write-failed';
      readonly phase: WritePhase;
      readonly failedFile: 'com' | 'canIf' | 'pduR';
      readonly message: string;
      readonly rolledBack: boolean;
    };
```

## Cycle-end Lessons (NEW permanent notes captured in PKM)

1. **`cross-file-atomic-from-snapshot-rollback`** (NEW, 1-of-1) — The 2-phase write pattern (snapshot originals to memory, write tmp files, atomic rename, rollback on failure using snapshot) is the standard way to compose per-file atomic operations into a cross-file transactional operation when staging dir + git are not available. Documents the failure mode + recovery semantics.
2. **`i18n-interface-split-by-domain-namespace`** (NEW, 1-of-1) — When a flat i18n interface approaches 1000 lines, split by domain namespace (app / dialog / dbc / odx) and re-export via barrel. Barrel re-export keeps all existing callers working without changes.
3. **Deferred-MEDIUMs-from-fix-review-must-be-ticketed** (1-of-1) — 3 MEDIUMs from v1.23.0 T2 fix-review sat in the PKM as "defer to v1.23.x PATCH" without a tracking ticket. v1.23.1 PATCH picked them up because the author remembered; future PATCH cycles should explicitly enumerate deferred MEDIUMs from prior reviews as candidate items.
